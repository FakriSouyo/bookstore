# Purpose

Define how the app generates PDFs: professional report documents (exported from `bookstore-reports`) and the receipt PDF fallback (from `bookstore-receipt`). PDFs are generated server-side with **pdfmake**, are printable on any device, and share one factory architecture for store header/footer, tables, and page numbering.

# Scope

- The PDF factory layer (`lib/pdf/`): document builder, store header/footer, tables, page numbering.
- Report PDFs (title, date range, filters, data tables, totals).
- Receipt PDF fallback (58/80mm portrait sheets).
- Filename and route conventions.
- Error handling and streaming.

Out of scope: report query logic (see `bookstore-reports`), receipt browser-print layout (see `bookstore-receipt`), schema (see `bookstore-database`).

# When to Use

Any task that produces a PDF: report export buttons, receipt "Print / PDF" fallback, or new printable documents (e.g., purchase order, inventory sheet). For reports, read `bookstore-reports` first; for receipts, read `bookstore-receipt`.

# Architecture

## Factory layout

```
lib/pdf/
├── document.ts      # buildDocument(docDef) → Buffer (pdfmake createPdf + getBuffer)
├── theme.ts         # fonts, colors, default styles (match bookstore-ui tokens)
├── headerFooter.ts  # store header block + footer with page numbers
├── tables.ts        # reusable table builders (data table, totals block)
├── reports.ts       # reportPdf(reportDef, data, params) — one factory per report family
└── receipt.ts       # receiptPdf(receiptData) — thermal-width PDF fallback
```

## Document conventions

- **Header** (every page): store name (from `store_settings`), address/phone, document title, generated-at timestamp. Subtle hairline under the header (border color from `bookstore-ui` tokens).
- **Metadata block** under the title: date range, filters applied (category/supplier/cashier), generated by.
- **Tables**: column widths in percentages, header row shaded with the app's background token, right-aligned money columns (tabular numbers), zebra or hairline rows, totals row bold with a top border.
- **Footer** (every page): store name + page number (`page X of Y` via pdfmake's `pageCount`).
- **Fonts**: embed a real font (e.g., Roboto via pdfmake's virtual file system) — default pdfmake fonts lack full Unicode; embed for book titles with non-ASCII characters. Numbers use the same font with tabular figures when available.
- **Landscape** for wide tables (movement ledger, inventory sheet) when the table exceeds portrait width; auto-set via a factory option.

## Report PDF route

`GET /api/reports/[key]/export?format=pdf` (see `bookstore-reports`): validate params → `requireRole('reports:view')` → run the report def → `reportPdf(...)` → stream `Content-Type: application/pdf` with `Content-Disposition: attachment; filename="<report>-<from>-<to>.pdf"`.

## Receipt PDF fallback

- Same data as the browser receipt (see `bookstore-receipt`), rendered as a single-page portrait sheet at the configured width (58mm ≈ 165pt content, 80mm ≈ 226pt content).
- Centered store header, item lines (title wrapped, qty × price right-aligned), totals block, payment/change lines, footer message.
- Used when: user chooses "Save PDF", the browser print dialog is unavailable, or thermal printing fails. The browser-print CSS remains the primary thermal path.

# Rules

1. PDFs are generated server-side only (pdfmake runs on Node). Never generate report PDFs in the browser.
2. All values are formatted from integer cents via `formatMoney`; no float rendering.
3. Every document carries the store identity (name/address/phone) and a generation timestamp.
4. Page numbering is mandatory for multi-page reports.
5. Report PDFs must match the on-screen report numbers exactly (same report def, same params).
6. Filenames are safe: `kebab-case`, `[a-z0-9-]`, no user input unescaped.
7. Errors: pdfmake failures map to `AppError('UNEXPECTED' | 'DATABASE_ERROR')` with a friendly message; never leak stack traces.
8. Receipt PDF is a fallback, not the thermal-print replacement — see `bookstore-receipt`.

# Implementation Guidance

```ts
// lib/pdf/document.ts
import PdfPrinter from 'pdfmake';
export async function buildDocument(docDef: TDocumentDefinitions): Promise<Buffer> {
  const printer = new PdfPrinter(fonts);          // embedded font VFS
  return new Promise((resolve, reject) => {
    const doc = printer.createPdfKitDocument(docDef);
    const chunks: Buffer[] = [];
    doc.on('data', c => chunks.push(c));
    doc.on('end', () => resolve(Buffer.concat(chunks)));
    doc.on('error', reject);
    doc.end();
  });
}
```

# Security

- The export route enforces `requireRole('reports:view')`; receipt PDFs enforce the sale's view scope (cashier may export only own sales' receipts).
- No user input is embedded into PDFs unescaped (titles, notes) — pdfmake escapes text by default, but keep notes/descriptions as plain text, never as HTML.
- Filenames sanitized; no path traversal.

# Performance

- pdfmake is CPU-light for our document sizes; generate per request.
- Stream the response rather than building giant in-memory strings for large reports.
- Cache the embedded font VFS in a module constant (loaded once).
- Bounded date ranges (see `bookstore-reports`) keep tables a reasonable size.

# Testing

- Unit: document builder returns a valid PDF Buffer (starts with `%PDF`), page count for multi-page fixtures, filename sanitization, money formatting in table cells.
- Integration: export route returns `application/pdf` with the right filename; a report PDF's table matches the CSV row count.
- E2E: "Export PDF" on a report downloads and opens (assert via response headers + content type; visual check optional).
- See `bookstore-testing`.

# Common Mistakes

- Client-side PDF generation (heavy, inconsistent, leaks data into the browser bundle).
- Default pdfmake fonts → missing glyphs for book titles with non-ASCII characters.
- No page numbers / footer on multi-page reports.
- Float money in PDF tables.
- Filenames with user input or slashes.
- Raw error leaks when pdfmake throws mid-generation.
- Receipt PDF replacing the actual thermal print path instead of supplementing it.

# Examples

**Report export route (abridged):**

```ts
export async function GET(req: NextRequest, { params }: { params: { key: string } }) {
  await requireRole('reports:view');
  const def = REPORTS[params.key];
  const query = Object.fromEntries(new URL(req.url).searchParams);
  const parsed = def.params.parse(query);               // zod, bounded dates
  const data = await def.run(ctx, parsed);
  const pdf = await reportPdf(def, data, parsed);       // Buffer
  const filename = `${def.key}-${parsed.date_from}-${parsed.date_to}.pdf`;
  return new Response(pdf, { headers: {
    'Content-Type': 'application/pdf',
    'Content-Disposition': `attachment; filename="${filename}"`,
  }});
}
```
